## 3. Как устроены программы у принятых работ и совпадают ли с нашими соглашениями

Единственный образец под ТЗ того же вида (кольцевой буфер, клавиатура 4×3/3×4, рис. 7) — **Осипова, А-12-22, вар. 12, 2025**.
Работы 2017–2023 делались по другому ТЗ (АЦП, UART, 2 знакоместа) — брать оттуда можно только приёмы.

### 3.1. Программа 1 — клавиатура (коды Осиповой, Keyboard.asm, с. 1–3)
- Бегущий ноль: маска `11111110b` сдвигается `rl A`. Для каждого столбца: `movx @DPTR,A` → `movx A,@DPTR` →
  `anl A,#00000111b` (3 строки) → `cjne A,#07h` (есть нажатие).
- Строка определяется через `cjne` с точными образцами 110b/101b/011b. Код — `mul AB`: строка·3 + столбец + 1. Последний
  столбец разбирается отдельно: 10, 11, 0.
- Сканирование останавливается на **первом** столбце с одиночным нажатием. Две клавиши в разных столбцах дают код первой.
  В ПЗ2 это честно описано («фиксирует нажатие в строке, расположенной выше», ПЗ2 с. 22), хотя ТЗ требует 0FFh.
- В конце — `clr A` / `movx` (все столбцы в 0, «для возможности формирования следующего прерывания»). `clr IE0` нет.
- **`call ScanKeyboard; %proc%` стоит в основной программе после инициализации, вектор INT0 — заглушка** (строки 42–44, 104).
  В ПЗ2 при этом нарисован обработчик INT0 (рис. 3.4).
- Регистры R0–R3 через `EQU` с говорящими именами, заголовок процедуры — блок между строками `; ====`.

**Сравнение с нами.** Маска строк, бегущий ноль, столбцы в 0 после опроса — совпадают. Расхождения:
- мы требуем 0FFh при двух клавишах в разных столбцах — это прямо из ТЗ (табл. 1: код «единственной нажатой клавиши или 0ffh»);
- мы требуем `call` в обработчике INT0: ТЗ называет программу «процедура обработчика IRQ клавиатуры» (табл. 1). Код Осиповой
  с вызовом из main наш чекер завалит («процедура не вызвана за 50 мс»). Принял ли такой вариант робот — неизвестно.

### 3.2. Программа 2 — чтение буфера (Ring.asm, с. 4–6)
- «Хвост» → DPTR, `movx A,@DPTR`, `inc DPTR`. Заворот: после `BUFFER_END` (0DDEFh) сравниваются оба байта с END+1, потом
  переход на START. Новый хвост сохраняется. Если хвост = голова, ставится `empty_flag`, иначе снимается. `overflow_flag`
  снимается всегда.
- **Проверки «пусто» перед чтением в коде нет.** В ПЗ2 (с. 19) написано, что она есть: «начинается с проверки флага пустоты… если
  он возведён, процедура завершается без чтения».
- Вызов из main (`call ReadFromBuffer; %proc%`) — как у нас.

### 3.3. Программа 3 — индикация (Indicator.asm, с. 7–8; вариант 2025 года, T3 на Timer1)
- `movc A,@A+DPTR` по таблице `SEGMENT_TABLE` (0–9, ОК). **Нет символа «E» (код 10) и гашения для кодов ≥ 11**, границы кода
  не проверяются. ТЗ (табл. 2) требует и то и другое, наш чекер это проверяет.
- T3 отсчитывается так: первая неполная загрузка (27488 мкс) плюс N полных переполнений по 65536 мкс (`T1_OV = 43`, режим 1,
  перезагрузки в обработчике нет). Вариант точный: нет накопления ошибки от перезагрузки на каждом тике.
- Обработчик на 1Bh — `call ProcessTimer1` / `reti`. `ProcessTimer1` сохраняет **PSW, ACC, DPL, DPH** (push/pop). Флаг
  `ind_flag_bit` делит один таймер между Y1 и индикацией — так советует методичка, с. 5.
- Константа первой загрузки: `HIGH(~TIMER_FIRST_LOAD)` — это 65535 − X, а не 65536 − X (ошибка на 1 мкс).

### 3.4. Буфер: семантика «полон / переполнение» — **главное расхождение**
- **Методичка-2026, с. 14:** голова — ячейка для записи, хвост — для чтения (у нас так же). Пусто — «хвост догнал голову
  (адреса совпали)». Переполнение — «голова догнала хвост (в момент записи голова указывает на ячейку перед хвостом, а после неё
  адреса совпадают)… необходимо ещё передвинуть указатель "хвост"». Получается, что по методичке равенство указателей после
  записи — уже переполнение: хвост сдвигается, одна ячейка теряется, в буфере максимум V − 1 отсчётов.
- **Осипова**, ПЗ2 рис. 3.10 и с. 23: INT1 — снять флаг пустоты, записать по голове, голова++; если голова = хвост — флаг
  переполнения и хвост++; иначе флаг переполнения снять. Это ровно методичка.
- **Мы** (`code-guide.md` разд. 3): полный буфер = HEAD = TAIL при F_EMPTY = 0, в нём V отсчётов, затирание — только на (V+1)-й записи.
- **Итог:** программа «как в методичке» у нас падает. В записи — сценарии «последняя свободная ячейка» (ждём хвост на месте)
  и «переполнение» (стартовое состояние HEAD = TAIL, F_EMPTY = 0 по методичке не бывает). В чтении — сценарий «полный буфер»
  (HEAD = TAIL, F_EMPTY = 0: процедура по методичке примет его за пустой) (`progs.go`, строки 212–222).
  Если руководитель проверяет по своей методичке, наш вариант тоже нужно уметь объяснить.

### 3.5. Прочие соглашения
- `X1`, `X2` — имена из ТЗ (табл. 1: «переменные в ОЗУ: X1, X2»). Это совпадение с ТЗ, а не наше изобретение.

### 4.4. Как считают ответы «п. 2.3»
- **Время заполнения:** t_min = V / f_max при X1 = 0 (Y2 пассивен, буфер не читается — ТЗ-2026, с. 5). В 2026 f_max = 4 отсчёта/с
  (ТЗ-2026, с. 5), в 2025 было 5. По методичке в буфер влезает V − 1 отсчётов (переполнение на V-й записи, см. 3.4) — стоит
  оговорить, какая семантика в коде.
- **Глубина стека (худший случай):** по лекциям (ч2, с. 4, 18) — адрес возврата 2 байта на каждый уровень прерывания и на каждый
  `call` плюс всё, что сохранено push. Высокий приоритет может прервать низкий, поэтому худший случай — сумма максимальных цепочек
  по двум уровням приоритета. У Осиповой — 2 байта (с. 25). У нас — MaxSP − 07h, измеренный в эмуляторе на сценариях программы 1.
